# 1. ЗАГАЛЬНА КОНЦЕПЦІЯ

## 1.1. Призначення продукту

MedCanvas — багатокористувацька, мультитенантна хмарна система управління стоматологічною клінікою, яка об'єднує адміністративні, клінічні та базові фінансові процеси в одному робочому просторі.

Головна цінність продукту — інтеграція наявного функціонального рушія одонтограми у повний робочий цикл клініки.

Система повинна забезпечувати безперервний зв'язок між пацієнтом, записом на прийом, клінічним оглядом, стоматологічною картою, планом лікування, виконаними процедурами, рахунком і наступним візитом.

## 1.2. Основний сценарій MVP

**Сценарій E2E-MVP-001: Повний цикл обслуговування пацієнта**

1. Адміністратор знаходить або створює пацієнта.
2. Адміністратор записує його до конкретного лікаря на доступний час.
3. Лікар бачить запис у власному розкладі.
4. Лікар відкриває картку пацієнта та переглядає доступну медичну історію.
5. Лікар розпочинає клінічний прийом.
6. Відкриває інтерактивну одонтограму, вносить клінічні дані та зберігає їх.
7. Створює план лікування із зазначенням процедур, зубів, вартості та етапів.
8. Система формує кошторис за узгодженим планом.
9. Лікар позначає фактично виконані процедури.
10. Адміністратор створює рахунок за виконані послуги.
11. Адміністратор реєструє демонстраційну оплату без реальної фінансової транзакції.
12. Лікар завершує прийом.
13. Адміністратор записує пацієнта на наступний візит.
14. Усі дані залишаються пов'язаними з правильною клінікою, пацієнтом і клінічним випадком.

**MVP вважається функціонально завершеним, лише якщо цей сценарій проходить від початку до кінця без ручного редагування бази даних або підміни відповідей API.**

# 2. МЕЖІ MVP

## 2.1. Обов'язково реалізувати

- SaaS Workspace для окремих клінік.
- Автентифікацію користувачів та авторизацію за ролями.
- Початкове створення клініки, персоналу та членства.
- Список і картки пацієнтів.
- Пошук, створення й редагування пацієнтів.
- Календар записів і графіки лікарів.
- Облік робочих кабінетів або стоматологічних крісел.
- Початок, ведення та завершення клінічного прийому.
- Інтеграцію наявної одонтограми та пародонтальної карти.
- Безпечне збереження клінічних даних і історію ревізій.
- Структурований план лікування.
- Каталог процедур і ціни.
- Автоматичний розрахунок кошторису.
- Реєстрацію виконаних процедур.
- Генерацію внутрішнього рахунку.
- Симуляцію часткової та повної оплати.
- Повторний запис пацієнта.
- Мінімальну робочу панель клініки.
- Журнал критичних дій.
- Повну автоматизовану перевірку ключових бізнес-сценаріїв.

## 2.2. Не входить до MVP

- Складський облік та закупівлі.
- Управління зуботехнічними лабораторіями.
- Складна CRM та маркетингові кампанії.
- AI-діагностика.
- Автоматичне встановлення діагнозів за знімками.
- Повноцінний DICOM/PACS.
- Інтеграція з ЕСОЗ.
- Страхова медицина.
- Інтеграція з банками, еквайрингом та реальними платіжними системами.
- Фіскалізація РРО/ПРРО.
- Реальне автоматичне списання SaaS-підписок.
- Повна бухгалтерія.
- Мобільний застосунок Android/iOS.
- Пацієнтський портал.
- Складна мережева структура клінік із централізованим холдингом.

Архітектура повинна дозволяти поступове додавання цих модулів без переписування наявних.

Один глобальний `User` може належати до кількох незалежних клінік через `ClinicMembership`.

Кожна клініка має власні:

- Пацієнтів.
- Працівників і призначені ролі.
- Лікарські графіки.
- Записи на прийом.

- Плани лікування.
- Каталог процедур і ціни.
- Рахунки та демонстраційні оплати.

Дані різних клінік не повинні змішуватися.

# 4. ТЕХНОЛОГІЧНА АРХІТЕКТУРА

## 4.1. Frontend

Базові технології:

- React.
- TypeScript.
- Vite.
- React Router для сторінок Workspace.
- TanStack Query для серверного стану.
- Поточна система компонентів і стилів із можливістю поступового впорядкування.
- Vitest для модульних та інтеграційних тестів.
- Playwright для браузерних E2E-тестів.

Клінічний рушій одонтограми залишається окремою підсистемою.

Заборонено змінювати SVG-алгоритми, клінічні стани, наявний публічний API та серіалізацію без підтвердженої необхідності.

## 4.2. Backend

Зберігається поточний стек:

- .NET 10 / ASP.NET Core Web API.
- Clean Architecture.
- CQRS / MediatR.
- FluentValidation.
- Entity Framework Core.
- PostgreSQL.
- JWT та існуючі політики авторизації.
- xUnit та PostgreSQL Testcontainers.

Архітектурний принцип: **модульний моноліт**.

Нові модулі розширюють наявні Domain, Application, Infrastructure та API. Мікросервіси не створюються в межах MVP.

## 4.3. Мультитенантність

Для MVP використовується спільна PostgreSQL-база з логічною ізоляцією за `ClinicId`.

Обов'язкові правила:

1. Tenant визначається з перевіреного сервером контексту автентифікації.
2. Кожен ресурс клініки має однозначну приналежність до tenant.
3. Усі запити повинні перевіряти активне членство й доступ до клініки.
4. `ClinicId` із тіла запиту не може перевизначати авторизовану клініку.
5. Пряме звернення до ресурсу іншої клініки за UUID не повинно розкривати його існування або вміст.
6. База повинна мати відповідні індекси, зовнішні ключі й перевірки зв'язків.
7. Всі нові модулі мають проходити негативні тести ізоляції.

## 4.4. Загальні стандарти

- Час у БД: UTC.
- Часовий пояс інтерфейсу: часовий пояс клініки, типовий `Europe/Kyiv`.
- Грошові значення: `decimal`, валюта UAH.
- Основна мова: українська.
- Друга мова: англійська; користувацькі тексти не повинні бути жорстко зашиті в компоненти.
- API: `/api/v1`, JSON, структуровані помилки.
- Пагінація для великих колекцій.
- Сортування й фільтрація на сервері.
- Аудит важливих змін.
- Відсутність персональних і клінічних даних у звичайних логах.
- Дотримання доступності інтерфейсу, орієнтир — WCAG 2.2 AA.

Кожен модуль розробляється окремо.

Стандарт:

`main → feature branch → implementation → tests → PR → independent review → merge → updated main`

- Жодних прямих комітів у `main`.

- Включати документацію в той самий PR, що й реалізацію.

- Злиття — лише після підтвердження власника проєкту та перевірки CI.

# 6. МОДУЛІ MVP

# M00 — Clinical Safety Foundation

**Пріоритет:** критичний  
**Тип:** технічний модуль перед використанням реальних даних  
**Гілка:** `fix/mvp-clinical-safety-gate`

## Мета

Закрити відомі ризики збереження та відновлення одонтограми, щоб новий Workspace не успадкував потенційно небезпечні операції над клінічними записами.

## Функціональний обсяг

- Строга перевірка snapshot перед `recoverChart()`.
- Перевірка приналежності стану до правильного encounter.
- Захист нових редагувань під час перемикання encounter.
- Відновлення autosave після безпечного recovery.
- Правдиві статуси `dirty`, `saving`, `saved`, `error`, `conflict`, `recovery-required`.
- Захист від застарілих асинхронних відповідей.
- Узгодження Status/Plan у серверному FHIR-експорті.

## Acceptance criteria

- Некоректний snapshot не знімає recovery lock.
- Після невдалого recovery заборонені всі клінічні записи.
- Зміни, зроблені під час перемикання огляду, не зникають.
- Неможливо зберегти стан одного пацієнта під encounter іншого.
- Autosave правильно відновлюється або залишається вимкненим згідно з явно заданою політикою.
- `saved` не відображається без актуального підтвердження збереження.
- FHIR Plan не генерує нових процедур на основі незмінених станів Status.

# M01 — SaaS Workspace, Identity & Clinic Context

**Пріоритет:** критичний  
**Гілка:** `feat/mvp-workspace-identity`  
**Залежності:** M00

## Мета

Перетворити автономну одонтограму на багатосторінкову SaaS-платформу.

## Функціональні вимоги

**FR-001 — Автентифікація**

Користувач може увійти до MedCanvas, вийти, отримати профіль і побачити власну активну клініку.

**FR-002 — Початкове створення клініки**

Передбачити безпечний механізм створення нового tenant і першого адміністратора.

Не дозволяти користувачу самостійно призначати собі адміністративну роль довільної існуючої клініки.

Для MVP можна використати контрольований онбординг без автоматичної SaaS-оплати.

**FR-003 — Членство персоналу**

ClinicAdmin може запрошувати працівника, призначати роль, відкликати доступ і переглядати перелік персоналу.

**FR-004 — Перемикання клініки**

Якщо користувач має членство в декількох клініках, він може вибрати активну клініку.

При перемиканні мають очищатися або перевірено переналаштовуватися всі клієнтські кеші та контексти, пов'язані з попереднім tenant.

**FR-005 — Workspace**

Передбачити:

- Основну навігацію.
- Dashboard.
- Пацієнтів.
- Календар.
- Прийоми.
- Плани лікування.
- Рахунки.
- Налаштування клініки.
- Профіль користувача.

Модулі, які ще не реалізовані, не повинні демонструвати фальшиву функціональність.

## Acceptance criteria

- Користувач може увійти та потрапити в Workspace своєї клініки.
- Інша клініка недоступна без активного членства.
- Ролі реально перевіряються сервером.
- Після виходу доступ до захищених сторінок відсутній.
- Перемикання клініки не показує кешовані дані іншого tenant.
- Нинішній одонтограмний рушій і його публічний API залишаються працездатними.

# M02 — Patient 360

**Пріоритет:** критичний  
**Гілка:** `feat/mvp-patients`  
**Залежності:** M01

## Мета

Створити повноцінний інтерфейс управління пацієнтами поверх уже існуючого Patient API.

## Функціональні вимоги

**FR-101 — Створення пацієнта**

Поля:

- Ім'я.
- Прізвище.
- Дата народження, якщо відома.
- Стать, якщо надана.
- Телефон.
- Email.
- Внутрішній номер медичної картки.
- Медичні попередження.
- Додаткова інформація у межах окремо визначених дозволених полів.

Обов'язковими мають бути лише поля, необхідність яких підтверджена бізнес-правилами.

**FR-102 — Список пацієнтів**

- Серверна пагінація.
- Пошук.
- Сортування.
- Фільтр активних/архівованих.
- Коректні порожні стани.
- Обробка помилок API.

**FR-103 — Картка пацієнта**

Розділи:

- Основні дані.
- Контакти.
- Медичні попередження.
- Історія візитів.
- Остання одонтограма.
- Плани лікування.
- Майбутні записи.
- Рахунки та історія демонстраційних оплат після реалізації відповідних модулів.

**FR-104 — Редагування**

Редагування демографічних і контактних даних із серверною валідацією.

**FR-105 — Архівування**

У MVP не видаляти фізично пацієнта разом із клінічною історією.

Передбачити архівування/деактивацію відповідно до правил зберігання медичних записів.

**FR-106 — Дублікати**

# M04 — Clinical Encounter Workspace & Odontogram

**Пріоритет:** критичний  
**Гілка:** `feat/mvp-clinical-workspace`  
**Залежності:** M02, M03, M00

## Мета

Лікар відкриває пацієнта, проводить огляд і працює з його одонтограмою у межах конкретного клінічного прийому.

## Основний сценарій

1. Лікар бачить свій календар.
2. Відкриває запис пацієнта.
3. Переглядає основну інформацію та медичні попередження.
4. Розпочинає `DentalEncounter`.
5. Вносить причину звернення та клінічні нотатки.
6. Відкриває поточну одонтограму.
7. Вносить зміни у Status.
8. За потреби працює з Plan.
9. Зберігає інформацію.
10. Повертається до картки пацієнта або завершує прийом.

## Основні правила

**FR-301 — Appointment ≠ Encounter**

Запис у календарі не є клінічним оглядом.

Огляд створюється окремо, коли лікар фактично починає прийом.

Потрібно встановити надійний зв'язок між Appointment та Encounter.

**FR-302 — Клінічні нотатки**

Лікар може додавати або змінювати нотатки до завершення прийому.

**FR-303 — Одонтограма**

Повторно використати наявний клінічний рушій.

Не створювати альтернативної реалізації одонтограми.

**FR-304 — Autosave**

Зміни зберігаються безпечно з ETag/concurrency-контролем.

**FR-305 — Історія**

Історичні ревізії одонтограми залишаються доступними для авторизованого перегляду.

**FR-306 — Завершення прийому**

Після завершення клінічні дані не можуть непомітно змінюватися заднім числом. Коригування мають оформлюватися за явно визначеним процесом.

## Acceptance criteria

- Одонтограма відкривається для правильного пацієнта.
- Перехід між пацієнтами не змішує клінічні стани.
- Дані залишаються після оновлення сторінки.
- Конфлікт версій не знищує локальні зміни.
- Завершений прийом захищений від несанкціонованого редагування.
- Старі ревізії доступні лише авторизованим користувачам.
- Медичні дані не потрапляють у логи.

- Значення поза діапазоном.
- Некоректний enum.
- Некоректний UUID.
- Невідповідність пов'язаних сутностей.
- Дубль.
- Невалідний стан ресурсу.
- Спробу змінити незмінні серверні поля.

Для дат додатково перевіряти граничні значення, часові пояси та переходи літнього часу.

Для фінансових сум — точність decimal, округлення, нуль, від'ємні значення, максимальні суми та конкурентні зміни.

## 7.3. Unit tests

Перевіряти:

- Доменні інваріанти.
- Бізнес-правила.
- Валідатори.
- Розрахунки.
- Машини станів.
- Обробку помилок.
- Мапінг моделей.
- Компоненти та їхню поведінку.

## 7.4. Application tests

Перевіряти всі важливі CQRS commands та queries:

- Успішний сценарій.
- Невалідний сценарій.
- Недостатні права.
- Відсутній ресурс.
- Конфлікт.
- Скасування операції.
- Ідемпотентність.
- Правильні побічні ефекти.
- Відсутність побічних ефектів після помилки.

## 7.5. Database integration tests

Використовувати реальний PostgreSQL через Testcontainers.

Перевіряти:

- EF Core configurations.
- Міграції.
- Унікальні обмеження.
- Зовнішні ключі.
- Tenant isolation.
- Конкурентні транзакції.
- Атомарність.
- Відновлення після помилки.
- Індекси для важливих запитів.
- Історію змін.
- Збереження decimal без втрати точності.

Не використовувати EF InMemory як єдине підтвердження поведінки PostgreSQL.

## 7.6. API integration tests

Кожен endpoint має перевірятися через справжній ASP.NET Core HTTP pipeline.

Обов'язкові результати, де застосовно:

- `200 OK`.
- `201 Created`.
- `204 No Content`.
- `400 Bad Request`.
- `401 Unauthorized`.
- `403 Forbidden`.
- `404 Not Found`.
- `409 Conflict`.
- `412 Precondition Failed`.
- `428 Precondition Required`.

Перевіряти реальні JSON-контракти, заголовки, content type, model binding та формат помилок.

## 7.7. Security & Tenant Isolation tests

Створити мінімум дві незалежні тестові клініки:

`Clinic A` та `Clinic B`.

Перевіряти, що користувач A не може:

- Отримати пацієнтів B.
- Прочитати огляди B.
- Переглянути календар B.
- Змінити процедури B.
- Отримати рахунки B.
- Створити фінансову операцію B.
- Підставити чужі ID у власні запити.
- Переглянути клінічну історію B.
- Отримати файли або записи B через прямий URL.

Повторити критичні сценарії з різними ролями.

## 7.8. Frontend integration tests

Для кожного екрана перевіряти:

- Початкове завантаження.
- Реальну відповідь API або контрактно точну тестову відповідь.
- Порожній список.
- Некоректну форму.
- Успішне збереження.
- Серверну помилку.
- Відсутність мережі.
- Повторення запиту.
- Недостатні права.
- Застарілі асинхронні відповіді.
- Відсутність дубльованих дій.
- Поведінку на планшеті та вузькому екрані.
- Клавіатурну навігацію та доступність.

## 7.9. E2E tests

Наприкінці кожного модуля мінімум один реальний браузерний сценарій повинен пройти через:

`UI → API → Database → API → UI`

Для основного MVP — обов'язково перевірити повний сценарій із розділу 1.2.

Тести мають використовувати синтетичних пацієнтів.

## 7.10. Concurrency & resilience testing

Обов'язково перевіряти ситуації:

- Два користувачі одночасно редагують той самий ресурс.
- Два адміністратори бронюють один час.
- Подвійне натискання кнопки.
- Повтор запиту після timeout.
- Відповіді приходять не в тому порядку.
- Запит завершився після переходу на іншу сторінку.
- Скасування операції.
- Конфлікт версій.
- Повторна спроба після помилки.
- Часткова відмова сервера.
- Неможливість підключитися до БД.

У всіх випадках дані повинні залишатися консистентними або система повинна явно повідомити про неможливість завершити дію.

## 7.11. Code coverage

Орієнтири для нового бізнес-коду:

- Domain/Application: ціль від 90% line coverage.
- Для критичних бізнес-переходів: прагнути до повного покриття значущих сценаріїв та гілок.
- Інші шари: вимірювати покриття, пояснювати прогалини.

Цифрове покриття не замінює тестів поведінки.

Не можна додавати порожні або штучні тести лише для збільшення відсотків.

# 10. ГЛОБАЛЬНІ ПРОДУКТОВІ ІНВАРІАНТИ

Ці правила мають залишатися чинними в усіх модулях.

**INV-001 — Tenant Isolation**

Жодні дані незалежних клінік не змішуються.

**INV-002 — Patient Ownership**

Кожен клінічний запис належить конкретному пацієнту та клініці.

**INV-003 — Clinical Data Integrity**

Одонтограма іншого пацієнта не може бути випадково збережена в поточний encounter.

**INV-004 — Historical Integrity**

Попередні ревізії медичних записів не можна непомітно перезаписувати.

**INV-005 — Appointment Integrity**

Активні записи не можуть конфліктувати за одним лікарем або ресурсом у той самий час.

**INV-006 — Treatment Integrity**

Запланована процедура не вважається виконаною без явного підтвердження.

**INV-007 — Financial Integrity**

Ціни та суми рахунків обчислюються сервером.

**INV-008 — Simulation Integrity**

Демонстраційні оплати не можуть подаватися як реальні фінансові транзакції.

**INV-009 — Authorization Integrity**

Роль і приналежність до клініки перевіряються на кожній захищеній серверній операції.

**INV-010 — No Silent Data Loss**

Помилки мережі, конфлікти версій і незавершені асинхронні операції не повинні мовчки видаляти незбережені клінічні зміни.

**INV-011 — No Hidden Clinical Automation**

Система не повинна автоматично встановлювати клінічний діагноз або позначати лікування виконаним лише на підставі зміни графічного стану зуба.

**INV-012 — Auditability**

Критичні зміни клінічних і фінансових записів мають бути відстежуваними.

# 11. ФІНАЛЬНИЙ E2E-СЦЕНАРІЙ ПРИЙМАННЯ

**Test Case:** `E2E-MVP-001 — Complete Dental Clinic Workflow`

### Початкові умови

- Створено Clinic A.
- Створено Clinic B для перевірки ізоляції.
- У Clinic A є ClinicAdmin, Clinician та Assistant.
- Є хоча б один доступний стоматологічний кабінет.
- Налаштовано прайс-лист.
- Усі дані синтетичні.

### Сценарій

**Крок 1 — Реєстрація пацієнта**

Адміністратор створює пацієнта.

Очікується: запис зберігається, відображається в списку і належить Clinic A.

**Крок 2 — Запис на прийом**

Адміністратор вибирає дату, лікаря, час і крісло.

Очікується: запис створено, конфліктів немає, лікар бачить його у власному календарі.

**Крок 3 — Відкриття картки**

Лікар відкриває пацієнта з календаря.

Очікується: правильні персональні дані, історія і медичні попередження.

**Крок 4 — Клінічний огляд**

Лікар починає Encounter, додає нотатки та редагує одонтограму.

Очікується: правильний зв'язок між Appointment, Patient, Encounter та Odontogram.

**Крок 5 — План лікування**

Лікар додає дві або більше процедур до плану.

Очікується: коректні зуби, етапи, ціни та загальна сума.

**Крок 6 — Виконання процедур**

Лікар позначає частину процедур виконаними.

Очікується: історія лікування оновлена; невиконані процедури залишилися запланованими.

**Крок 7 — Рахунок**

Адміністратор створює рахунок за виконані процедури.

Очікується: сума правильна, дублювання процедур немає.

**Крок 8 — Симуляція оплати**

Адміністратор реєструє часткову й потім повну демонстраційну оплату.

Очікується: залишок і статус оновлюються, записи явно позначені як симуляція.

**Крок 9 — Завершення прийому**

Лікар завершує Encounter.

Очікується: історичні клінічні дані захищені від несанкціонованого редагування.

**Крок 10 — Наступний візит**

Адміністратор створює новий Appointment із контексту пацієнта або плану.

Очікується: новий запис прив'язаний до того самого пацієнта й має незалежний життєвий цикл.

**Крок 11 — Перевірка ізоляції**

Користувач Clinic B намагається отримати дані Clinic A через API.

Очікується: доступ заборонено без розкриття медичних даних.

**Крок 12 — Перевірка відновлення**

Перезапустити браузер і повторно відкрити Clinic A та пацієнта.

Очікується: усі підтверджено збережені дані відновлюються; немає змішаних клінічних станів.

### Критерій приймання

Тест має проходити повністю через реальний UI, API та PostgreSQL, використовуючи лише тестові дані.

Жоден крок не повинен вимагати ручного SQL або підміни готових результатів.

# 12. КРИТЕРІЇ ЗАВЕРШЕННЯ ВСЬОГО MVP

MVP вважається функціонально реалізованим, коли:

1. Завершені й прийняті всі модулі M00–M09.
2. Основний E2E-сценарій проходить.
3. Ізоляція двох незалежних клінік підтверджена.
4. Календар не допускає конфліктних бронювань.
5. Одонтограма працює з реальним бекендом та історією ревізій.
6. Плани лікування мають структуровані пункти й правильні суми.
7. Виконані процедури правильно пов'язані з пацієнтом та оглядом.
8. Рахунки та симуляції оплат працюють без математичних і транзакційних помилок.
9. Можна призначити наступний візит.
10. Всі необхідні автоматизовані тести проходять.
11. Критичні знайдені дефекти виправлені.
12. Бекенд і фронтенд документовані.
13. Демонстраційне середовище можна розгорнути й відтворювано протестувати.
14. Є окремий список вимог для переходу від демонстраційного MVP до використання реальними клініками.

**MVP, готовий до демонстрації, не означає автоматично MVP, дозволений для зберігання справжніх медичних карток.**

Перед реальним клінічним пілотом обов'язково підтверджуються:

- Правова підстава обробки медичних персональних даних.
- Договори та відповідальність сторін.
- Шифрування даних і резервних копій.
- Контроль доступу та журналювання.
- Перевірене резервне відновлення.
- Захист файлового сховища.
- Реагування на інциденти.
- Безпекове тестування.
- Розмежування демонстраційних і реальних фінансових процесів.

- Переходити від симульованих до реальних платежів.
- Автоматично мержити PR.
- Оголошувати MVP готовим без критеріїв приймання.

Кожна суттєва зміна обсягу оформлюється як оновлення ТЗ або окреме рішення щодо продукту.

# 14. ПІДСУМКОВЕ РІШЕННЯ

MedCanvas MVP розробляється як **єдина, модульна, багатокористувацька стоматологічна SaaS-система** для повного циклу роботи невеликої клініки.

Основний напрямок розвитку:

**SaaS Foundation → Patient 360 → Scheduling → Clinical Encounter → Treatment Planning → Procedure Execution → Demo Billing → Follow-up → E2E Verification.**

Кожен модуль має:

- Чітко визначені функціональні вимоги.
- Власну Git-гілку.
- Власний Pull Request.
- Реальні backend/frontend зміни.
- Валідатори.
- Повноцінні тести бізнес-правил та CRUD.
- Інтеграційні тести API і PostgreSQL.
- Перевірку ролей і мультитенантності.
